# 生词本的导入导出格式改为 CSV

生词本与外部交换的数据用 CSV(RFC 4180,UTF-8 带 BOM),首行是表头:
`term,normalized,sourceLang,targetLang,translation,phonetic,partOfSpeech,addedAt`。

选 CSV 而不是 JSON,是因为这份数据的第一用途是给人看、给人改、给别的工具吃(Excel、Sheets、Anki 导入)。JSON 对脚本友好,但想改一个译法还得数括号。CSV 用逗号、引号和换行都按标准转义,字段顺序可调,少一列可选字段也能导入。

导出与导入都走文件,不经过面板里的文本框:

- **导出**调用 `showSaveFilePicker` 让用户选择保存位置;引擎没有该 API(或用户脚本沙箱里拿不到)时退回 `blob:` + `<a download>`,仍然落进浏览器的下载流程。文件名形如 `生词本-2026-10-26.csv`。
- **导入**用 `<input type="file">`,这是唯一在桌面、手机、Firefox 上都能用且不要求安全上下文的文件选择方式。
- **覆盖还是合并,在读入文件之后再问**。先弹选择框再问策略,会在用户取消选择时留下一个悬空的问题;先读文件,才能顺带告诉他「现有 N 条」,这个数字正是他判断覆盖代价的依据。覆盖只在文件解析通过、表头校验通过、且至少有一行可用之后才清空现有词条:拿错文件、空文件、内容全坏的文件都不会清空生词本。

几个刻意的取舍:

- **不导出 `entryId`**。它是 `sourceLang + '|' + normalized` 算出来的,写进文件就有两份真相,手改后可能互相矛盾。导入时重新计算,身份规则仍只有 `GLOSSARY.md` 里那一处。
- **必填列**是 `sourceLang`、`targetLang`、`translation`,以及 `term` / `normalized` 至少一个。缺值的行跳过并计入统计,整个文件缺列则直接报错——前者是数据脏,后者是拿错了文件,不该混为一谈。
- **公式注入防护只加在导出文件上**。词条文字来自任意网页,以 `=`、`+`、`-`、`@` 开头的单元格会在表格软件里被当成公式执行;导出时在单元格内加 `'` 前缀,导入时再剥掉。本机存储不加这个前缀——它只被本脚本读取,加了反而污染数据。
- **带 BOM** 是为了 Excel 在 Windows 上不按本地代码页读 UTF-8;导入时忽略 BOM,所以手工保存的 CSV 也能读。
- **本机持久化同期改为 CSV**,见 `docs/adr/0009`;这里定义的表头就是两边共用的那一份。

代价:0.3.x 导出的 JSON **文件**不再能导入(存储里的旧 JSON 值不受影响,由 0009 自动迁移)。若手上还有这样的文件,可按下表手工转成 CSV:列名对应,`entries` 数组里的每个对象就是一行。另一点是 `showSaveFilePicker` 只在 Chromium 系有效,Firefox 上永远是下载;两条路径写出的文件内容相同,只是「另存为」对话框的呈现不同。
