# 本机持久化也改用 CSV

Tampermonkey 的三个存储键全部改为 CSV 文本,与导出的文件用同一套解析器(`src/core/csv.js`):

| 键 | 形状 |
| --- | --- |
| `settings` | `section,key,value` 三列。标量在 `general` 段,`glossSites` / `targetOverrides` 每个站点一行,`disabledProviders` 每个源一行 |
| `entries` | 与导出文件完全相同的八列,只是不带 BOM |
| `cache` | `key,value,expires,used`,一次查询一行;`value` 是记录,所以那一个单元格里放 JSON |

理由和 0008 相同:本地能看到、能读懂、坏掉时能手工修。之前的 JSON blob 在开发者工具里是一行几百 KB 的字符串,想确认「某个站点为什么开了注音」只能靠读代码;现在是 `glossSites,example.com,true`。

几个刻意的取舍:

- **设置不塞进一行 `key,value`**。站点开关是主机名到值的映射,压平成一列就得把主机名编码进键名(`glossSites.example.com`),既不可读也不可 grep;用 `section` 列分段落,一眼能看出哪些行属于同一类设置。
- **类型靠约定还原**。CSV 只有文本,所以 `true` / `false` 还原为布尔,纯数字还原为数字,其余保持字符串。设置里就这三种类型;`targetLang` 之类的值不会写成纯数字,不用担心被误转。
- **`cache` 的 `value` 单元格里是 JSON**。译文是字符串,词典详情是嵌套记录,两者共用一张表,只有把记录塞进单元格这一种写法不改表结构。代价是引号被翻倍,`cache` 本来就是机器读的,不追求可读。
- **旧值仍然能读**。文本以 `{` 或 `[` 开头就按 JSON 解析一次,下次写入自然变成 CSV。这跟 0008 里「不猜导入文件格式」不冲突:那个是用户手工选的文件,猜错要误导人;这个是本脚本自己上一版写的值,读不出来就是丢数据。
- **坏值降级为空**。解析失败、引号未闭合、存储拒绝访问,一律当作「什么都没记住」,脚本照常启动——这是原有行为,换格式不能把它弄丢。

代价:`entries` 每次保存都要把整本生词本重新编码一遍,和原来 `JSON.stringify` 的代价同阶;`cache` 上限 5000 条,同样整表重写。真到了写不动的地步,该改的是「整表重写」这个策略,而不是格式。

**不能回退**:0.3.x 只会 `JSON.parse` 存储值,读到 CSV 会解析失败并当作空。升级后装回旧版,生词本会显示为空(数据仍在存储里,装回新版即恢复)。升级本身不需要任何准备:旧 JSON 值由 0008/0009 的读取路径自动迁移。真正的保险是在**升级之后、想回退之前**用 0.4.0 导出一份 CSV —— 0.3.x 只有 JSON 文本导出,那个文件不能作为 CSV 导入,所以「升级前先导出 CSV」这件事在旧版里根本做不到。
