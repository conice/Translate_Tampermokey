# 05: 注音刷新的清理范围

**What to build:** 关掉本站注音、或生词本变化触发刷新之后,页面完全恢复成原文,且不会因为清理而把整页的文本节点合并掉;在依赖节点身份的框架渲染页面上开关注音,内容不会错位或丢失。

**Blocked by:** 04 (改的是同一处注音样式与标记的清理逻辑)

**Status:** ready-for-agent

- [x] 刷新注音时不再调用整页的文本节点合并
- [x] 每个注音标记被换回它自己的原始文本,而不是被注音后的拼接文本替换
- [x] 只有当父节点的子节点全部是文本节点时才在该父节点上做合并,父节点含元素子节点时保持不动
- [x] 关闭本站注音后,页面文本与开启前完全一致,不残留标记元素或空标签
- [x] 反复开启/关闭注音不会让文本节点数量无限增长
- [x] 新增 DOM 测试:父节点含元素子节点时不被合并;只在文本节点之间合并时,合并范围不越出该父节点
- [x] 现有注音 DOM 测试全部保持通过

## Comments

**实现**

- `src/ui/gloss-layer.js`:清理逻辑从 `refresh` 里抽成 `restoreMarkers()`,并删掉 `document.normalize()`。
  - 每个标记用 `originalTextOf(marker)` 换回文本节点。首选标记的首个子节点(就是原文那一段);首个子节点不是文本时,从「除注音外的所有子节点」重建,而不是取 `marker.textContent` —— 后者会把译文一起拼进正文。
  - 合并只在被恢复过的父节点上做,且仅当该父节点的子节点**全部**是文本节点时。含元素子节点的父节点属于页面自己的结构,React/Vue 持有那些节点的引用,合并会让它的下一次重渲染把旧内容放回去、或放到错误的位置。
  - 整个恢复过程仍然包在 `suppressed = true` 里,所以合并产生的 childList 变更不会被自己的 MutationObserver 当成新内容再扫一遍。

**测试**(`test/gloss-layer.dom.test.mjs` 新增 5 条,共 21 条)

- 合并范围只到被恢复的父节点:两个段落各自恢复成一个文本节点。
- 父节点含 `<b>` 时不合并:断言该段落仍是 5 个节点,且 `<b>` 还是原来那个元素。
- 与注音无关的相邻文本节点保持原对象(这条是删掉 `document.normalize()` 的直接证据,改之前它是失败的)。
- 关闭注音后 `document.body.innerHTML` 与开启前逐字节一致,无标记、无空标签残留。
- 反复开关四次,文本节点数不再增长。

全量 196 条通过。

**一处刻意的取舍**

含元素子节点的段落只恢复文本、不合并,所以关闭注音后那一段会留下几个相邻的文本节点。页面文字完全一致,但节点数比开启前多。要合并就得跨越框架可能持有的节点,风险大于收益,已在 README 的「已知限制」里写明。
